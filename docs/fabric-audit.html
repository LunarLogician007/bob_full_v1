Every file in the repo traced to its origin, then measured against the four architectures you named. The logic block is faithful 7-series — the LUT fracture and carry chain are correct down to which output feeds the propagate term. Section 2

What already matches the references

Worth stating plainly before the flags, because it is the load-bearing part: the logic block is not an approximation of a 7-series slice, it is a correct one-LUT version of it. I checked each of these against the AMD text rather than from memory.

  • LUT6 fracture o5 taps the 5-input subtree, so INIT[31:0] serves O5 and INIT[63:32] serves O6 with i5 high. Exactly UG474's rule. UG474 · Look-Up Table
  • Carry chain Propagate from O6, generate from O5 or the bypass input, MUXCY + XORCY, chain running up the column. That is CARRY4's structure, one bit wide. UG474 · Carry Logic
  • Flip-flop priority sr beats ce and is synchronous, with a selectable reset value — FDRE/FDSE semantics, including the part people get wrong. UG474 · Storage Elements
  • TAP conformance EXTEST all-zeros, BYPASS all-ones, Capture-IR loading …01, IDCODE selected at Test-Logic-Reset, TDO and both update latches on the falling edge. IEEE 1149.1
  • Dark-on-zero An all-zero bitstream selects const0 everywhere, so an unconfigured fabric has no loops and drives nothing. Aegis specifies the same reset behaviour. Aegis · configuration.md
  • Config readback Capture-DR reloads cfg_dr from cfg_out, so every load is verifiable. Aegis has no readback path at all — this is ahead of the reference. ahead of Aegis

Section 3 · fourteen findings

Where it diverges, and whether that matters

Ordered by what they block. blocker means the roadmap item you asked about — BRAM, DSP — is not meaningful until it is fixed. scaling means it is fine at 4×4 and fails as the grid grows. dead feature means the hardware exists and nothing can reach it.

F1
scalingblocker

The switch box is a full crossbar. No silicon does this.

Each of the 16 switch-box outputs is a 20:1 mux over every source, and each of the 6 LUT inputs is another 20:1. In VTR's vocabulary that is Fs = 16 and Fc_in = 100% — a complete crossbar in every tile.

Bidirectional architectures in VPR use Fs = 3. Aegis's output mux picks only the same track index from each of four directions plus the CLB output — a 5:1 subset switch block. 7-series routing is nothing like either; it is a mix of singles, doubles and quads with sparse connectivity. bob is 4× richer than Aegis and roughly 5× richer than a VPR default, which is why the router is trivially easy and why 61% of the bitstream is routing selects.

At 4×4 this is a defensible research choice — it makes routing always succeed. It is also the single thing that will not survive going to 8×8. Make the pattern a parameter now, add Wilton with Fs = 3 as the alternative, and measure both in LUTs before you commit.

refs VTR arch reference (Fs/Fc, subset/wilton/universal) · aegis/docs/arch/routing.md · UG474 Interconnect Resources

F2
scaling

Every track is length 1, so every tile hop costs a mux

Crossing the grid costs one mux delay per tile, with no bypass. 7-series has singles, doubles, quads and long lines precisely to avoid this; VTR models it as segment length L. This is the real reason TCK is pinned at 1 MHz rather than anything about the JTAG link.

Add length-2 and length-4 segments before growing the grid — they cost sources in the mux bus, which is another reason to fix F1 first.

F3
blocker

There is no user clock. TCK clocks the fabric.

This is the most important finding in the audit. A user design only advances when the probe toggles TCK, which means sequential logic runs at whatever rate the USB link happens to manage. BRAM and DSP are not meaningful on a fabric with no free-running clock — a synchronous memory clocked by a debug probe is a shift register with extra steps.

Aegis puts this in a dedicated clock tile: four outputs, each with an 8-bit divider, phase select, duty control and a lock indicator, 49 config bits. AMD does it with BUFG and MMCM on a global clock network. bob has neither.

The PYNQ-Z2 has a 125 MHz oscillator and the PS FCLKs available. Bring one in through a BUFG, add a config-selected divider, and add a per-CLB clock-source bit so a tile picks TCK or the user clock. TCK then does configuration only — which also retires the awkward 1 MHz timing constraint, since the fabric's own clock domain becomes the thing you close timing on.

refs aegis/docs/arch/clock.md · UG472 Clocking Resources

F4
scalingblocker

The configuration chain is centralised, not distributed

cfg_dr (2896 bits) and cfg_out (2896 bits) both live inside jtag_tap.v, and cfg_out is a flat 2896-bit bus fanned out to the fabric. That is 5792 flops in one module and one very wide bus crossing the die.

Both Aegis and OpenFPGA's scan_chain protocol put the shift register and its shadow register inside each tile, daisy-chaining cfgIn → cfgOut, so the chain is placement-local and the top level carries four wires instead of thousands. At 16×16 bob's approach is 46,336 bits on a single bus; it will not place.

Fix it now while it is cheap. Move the shift and shadow registers into tile.v, give the tile cfg_in / cfg_out / cfg_shift / cfg_load, and keep the bit order identical so bitstream.py needs no change at all. It also opens the door to OpenFPGA's num_regions — independent chains per region, which is partial reconfiguration for free.

refs OpenFPGA config protocol (standalone / scan_chain / frame_based / memory_bank) · aegis/docs/arch/configuration.md

F5
scaling

Config memory is flip-flops; on a Xilinx host it needn't be

Two flops per config bit plus a 32-wide mux tree per routing mux is the generic way to build an overlay, and it is what ZUMA measured as the baseline before improving on it. ZUMA holds overlay LUTs and routing-mux selects in the host's LUTRAM instead, cutting resource use to under a third and bringing the overlay's area penalty down to roughly 40 host LUTs per overlay LUT.

The mapping is neat here: an overlay LUT6's 64 INIT bits are exactly one RAM64X1S in a SLICEM. This is the known answer if the grid is to get meaningfully bigger on a Z020.

ref Brant & Lemieux, ZUMA: An Open FPGA Overlay Architecture, FCCM 2012

F6
dead feature

The carry chain is built, modelled, and unreachable

CY_EN and CY_DI_SEL exist in the tile and are modelled correctly in simulate(). But no design in designs.py sets them, the fabric testbench never exercises them, and carry_out is tied straight into _unused in fpga4x4.v. The README's "a column of four tiles is a four-bit adder" is true of the RTL and not reachable from the toolchain.

There is also one cin shared by all four columns, from USER bit 2. 7-series gives each carry chain its own CYINIT so a slice can choose add or subtract independently; bob cannot. Expose carry_out in the USER status word, make cin per-column, add Design.adder(), and put an adder in the vector set.

F7
dead feature

The LUT5 pair — the whole point of lut6.sv — has no API

SRC_CLB_O5 is routable and Cell(r, c, 'o5') exists in bitstream.py, but Design.lut() only ever returns Cell(r, c, "o") and there is no Python equivalent of init_frac(). The fracture is unreachable, which halves the fabric's usable logic capacity on paper.

UG474's rule is that A6 must be driven High when both outputs are used. Nothing in the tooling enforces it. A Design.lut5_pair() that packs INIT = {hi5, lo5}, forces cb[5] = SRC_C1 and returns both cells fixes the gap and the hazard together.

F8
blocker

No I/O tile — the pad map is hard-wired in two places

Six inputs and three outputs, bolted to specific edges and tracks, with no direction control, no registers and no per-pad configuration. Aegis has an 8-bit IOTile: direction mode, input register, output register, output track select. AMD has the whole IOB/ILOGIC/OLOGIC stack.

The concrete hazard is that the map is written out twice — once in fpga4x4.v's edge assignments, once in bitstream.py's _sources_at() — with nothing checking they agree. Every heterogeneous tile you add will widen that seam. Generate both from one table.

ref aegis/docs/arch/io.md · UG471 SelectIO

F9
keep

Edge broadcast beats Aegis's wired-OR — keep it

bob broadcasts pad_i[3:0] to every row's west edge and pad_i[5:4] to every column's south edge. Aegis wired-ORs all edge tiles onto a shared edge signal, which means two tiles driving the same edge silently merge. Neither resembles silicon, which puts a real switchbox in the I/O ring — but bob's is the safer of the two. Keep the scheme; just generate it from the same table as F8.

F10
software phase

The router is BFS with no rip-up

Design._bfs() is first-come-first-served shortest path, and its seen set is keyed on the tile — once a tile is reached, it is never revisited on a different track. A congested design raises RouteError with no recovery. VPR, nextpnr and nextpnr-aegis all use negotiated congestion (PathFinder) instead.

You said software comes later and that is right. Flagging it because it caps how large a design you can use to prove the hardware — and the hardware work above will produce exactly the congested designs this router cannot handle.

F11
integrity

No bitstream integrity check

SELW is 5 bits for 20 sources, so 12 of 32 codes are illegal; mux_bank.v pads the bus to 32 and reads a hard zero. That is a good failure mode, but it means a corrupted bitstream is silently benign rather than detectable. Readback currently proves the chain round-tripped, not that the bits are the ones you meant.

7-series bitstreams carry a CRC. Aegis has none. A magic word at the head of the chain plus a CRC checked at Update-DR, driving a status bit, is cheap and turns "readback verified" into a real integrity claim.

F12
scaling

The switch box can reflect, which makes the shortest loops

An output mux for direction D can select the track arriving from direction D, so tile A → tile B → tile A is a two-tile combinational loop the bitstream can express. Forbidding same-direction sources per output removes the shortest loops at no cost and shrinks every switch-box mux from 20:1 to 16:1 — 4 sources × 16 muxes per tile.

Longer loops remain, so the LUTLP-1 downgrade still has to stay. That downgrade is the right call and the XDC's reasoning for it is sound. One consequence to carry into F3: once there is a real user clock, Vivado's arbitrary loop-breaking means WNS stays indicative, and you will need a deliberate max-delay strategy rather than a slow TCK.

F13
blocker

No utilisation or timing data is tracked in the repo

report.tex quotes LUTLP-1's "1569 LUT cells form a combinatorial loop" and that is the only resource number anywhere. There is no utilisation report, no WNS, no LUTs-per-tile figure.

For a hardware-first phase that number is the metric — it is what decides whether the next grid size fits. Emit report_utilization and report_timing_summary from create_project.tcl, commit them, and watch LUTs-per-tile move as F1 and F12 land.

F14
documentation

bsc_cell.v's header describes a different TAP encoding

The inherited header argues its synchronous-reset fix using ../both's state encoding — "TLR is 4'b0000", "Exit1-DR 0101 → Update-DR 1000". In bob, TLR is 4'b1111, Exit1-DR is 0001 and Update-DR is 0101. The fix is still correct and necessary, and jtag_tap.v's own header re-derives the hazard properly for this encoding. But the cell's argument, read on its own, is about a chip that isn't this one.

It also cites [FIX 1], [FIX 3], [FIX 5] and ps/probe_preload.py — none of which exist in this repo. Since the file is byte-identical to ../both on purpose, the honest fix is a short note at the top of bob's copy saying so, rather than editing it and losing that property.

Section 4

Phase A — make the base solid

Sequenced so each step unblocks the next. Nothing here adds a feature; all of it is making the fabric able to carry one. The vector harness — bitstreams from the engine, expected values from its own model, replayed through the RTL — is the best thing in the repo and every step below should extend it rather than route around it.

  1. User clock and a clock tile

    125 MHz oscillator through a BUFG, config-selected divider, per-CLB clock-source bit. TCK becomes configuration-only.

    unblocks F3 → everything sequential, and all of Phase B
  2. Distribute the config chain into tile.v

    Per-tile shift and shadow registers, four wires from the TAP. Bit order unchanged, so the bitstream format and bitstream.py are untouched.

    unblocks F4 → any grid larger than 4×4, and per-region partial reconfig
  3. Make FF, carry and fracture reachable

    Design.reg(), Design.adder(), Design.lut5_pair(); per-column cin; carry_out into USER status; a sequential path in simulate() so the model can express what the RTL already does.

    closes F6, F7 — three dead features, no new silicon
  4. A real I/O tile, generated from one pad table

    Direction, input register, output register, track select. RTL edge map and _sources_at() both generated from the same source.

    closes F8, F9 — and the seam widens with every heterogeneous tile
  5. Parameterise the routing pattern

    Keep the full crossbar as SB_PATTERN=full for the dev fabric; add Wilton Fs=3 and length-2 segments alongside. Drop same-direction reflection either way.

    closes F1, F2, F12 — measure both patterns before committing
  6. Commit utilisation and timing reports

    LUTs per tile is the budget that sets the grid size. Track it from here, not after the fabric has doubled.

    closes F13 — needed to make any Phase B sizing decision honest

Section 5

Phase B — BRAM and DSP tiles

Both AMD and Aegis specialise by column: the routing wrapper is identical in every tile and only the logic core differs. AMD calls it ASMBL; Aegis places BRAM and DSP columns at fixed intervals through the grid. Adopt that shape — it is the one structural decision that everything else in Phase B depends on.

The change to make first: bitstream.py assumes a uniform TILE_CFG_W everywhere. Make it a table indexed by tile type, and make fabric.v instantiate by column type, before you write the first line of BRAM. Retrofitting that later means rewriting the packer and every vector.

BRAM tile

Aegis specifies asynchronous, combinational reads. Do not copy that. AMD's RAMB18E1 and RAMB36E1 are fully synchronous for both read and write — and since you are hosting on a real 7-series part, that is not a style preference but a mapping constraint: an async-read overlay BRAM cannot become a host BRAM primitive at all, and would have to be built from distributed RAM at a few hundred bits per host LUT. Make the overlay BRAM synchronous-read and one tile becomes one RAMB18E1 at almost no LUT cost. The Z020 has 280 of them (140 RAMB36E1, splittable).

The width problem is the real design question. With NTRACK = 4, one tile edge carries four bits — nowhere near address plus data. Aegis's answer is to pack and truncate when the tracks are too narrow, which quietly drops address bits. AMD's answer is that a BRAM36 spans the height of several CLBs in its column. Take AMD's: let a BRAM tile occupy a column of four tile slots and gather its ports from all four edges. NTRACK stays uniform, and the carry chain passes through untouched, as it does in Aegis.

DSP tile

Aegis's DSP is an 18×18 unsigned multiply with a small mode field. Take AMD's shape instead, narrowed to fit: 18×18 signed into a 48-bit accumulator, a pre-adder, and — the part that matters most — a result cascade up the column, the way DSP48E1 chains PCOUT into the next slice's PCIN. That cascade is what makes DSP columns useful for FIR taps and wide multiplies, and it is free routing in exactly the way the carry chain already is. Building the DSP without it produces a multiplier you have to route around the fabric, which the fabric cannot afford.

Same width problem, same answer: a DSP tile spans a column. Target one host DSP48E1 per tile — the Z020 has 220.

Section 6

Which reference to trust for what

You asked to lean on the official docs, and you're right that AMD's are the best written. But they are not all answering the same question, and one of the four is not an architecture reference at all.

SourceUse it forWatch out for
AMD UG474 / 473 / 479 What a CLB, BRAM and DSP are. Also your mapping constraints, since the host is a 7-series part. Describes silicon with resources an overlay can't spend. Read for semantics, not for scale.
Aegis (local: ../aegis) The closest analogue to bob: small parameterised fabric, single scan chain, column-specialised BRAM/DSP, carry up a column. Best structural model you have. Two choices not to copy — async-read BRAM and the 5:1 subset switch box. Check each against AMD first.
OpenFPGA / VTR The vocabulary and the parameter space: Fs, Fc_in, Fc_out, segment length, switch-block pattern, config protocol. The standard way to describe what you built. A generator and a modelling flow, not a design. It won't tell you what to pick, only how to say it.
F4PGA (was SymbiFlow) Nothing yet. It targets existing silicon — 7-series via Project X-Ray, iCE40, ECP5, EOS-S3. Not an architecture reference. It becomes relevant in the bitstream and placement phase, not this one.
ZUMA (FCCM 2012) The one paper written about exactly your problem: an FPGA overlay on a commercial FPGA, and how to make it cost less. 2012, so its host is a Virtex-5/6. The LUTRAM technique carries over unchanged.

The short version. The logic block is good and correct 7-series, and the verification method — an independent software model cross-checking the RTL through generated vectors — is better than either reference project has. What is missing is everything around the logic block: a clock, a scalable config path, an I/O tile, and a routing pattern that came from somewhere.

A1 through A3 are the ones I would not start BRAM without. A clock especially — without it, a block RAM in this fabric is a shift register you talk to over USB.
