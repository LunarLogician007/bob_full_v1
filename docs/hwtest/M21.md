# M21 hardware test: the cluster CLB and the BRAM-shadow readback

**This milestone needs a Vivado rebuild.** `hw/build.cfg`:
- `tag = M21`
- `top = bob_top`
- `idcode = 0B021093`
- `usercode = 00000015` (21)
- `delays = 1`: time the element classes again, now with the crossbar
  (`hw/scripts/delay_samples.txt`, 1096 hops)

## What changed

**The CLB is a cluster** (OpenFPGA's k6_frac_N10 shape at N = 4, sized by measurement:
`docs/reports/M21/cluster_sweep.md`). Each CLB has:
- **4 logic elements.** Each element is one LUT6 or two LUT5s sharing five inputs, with a
  carry and **two** flip-flops.
- **16 inputs and 8 outputs.**
- **A full crossbar:** every element input picks any CLB input or any element's output.

The carry runs through the four elements, then to the CLB above.

| | M16 / M20 | M21 |
|---|---|---|
| CLBs | 100, one LUT each | 49, four LUTs each |
| LUTs | 100 | **196** |
| channel width | 24 | 40 |
| configuration | 18,560 bits, 145 frames | 32,896 bits, 257 frames |
| CAPTURE | 100 bits (one per CLB) | 392 bits (two per element) |
| pads | 44 | 32 |

- **Readback comes from a BRAM shadow** of the frames written (`cfg_store.v`,
  `docs/bitstream-format.md` §14). The 256:1 × 128 readback mux is gone; it was about a
  third of the design. Nothing on the wire changes.
- **What readback proves now:** the frames that were written, not what the configuration
  flip-flops hold. The flip-flops stay checked by CAPTURE against the golden netlist and by
  the live model checks.
- **Autostep fires one TCK after the pad update.** INTEST autostep used to clock the fabric
  about 30 ns after the boundary took the new inputs. That was too little for `fir`'s
  button → DSP → adder → `y` path, and it is the cause of M20's `bob-fir` failure.
- **`clock_ctrl.v` registers its period and gap values.** M20's build missed timing by
  0.919 ns on `per_m1 → cnt` (98 endpoints). The values are static while the fabric runs,
  so one cycle of latency costs nothing.
- **Vivado no longer times the empty fabric; the software does, per design.** The first
  M21 implementation placed at WNS −133 ns on fabric paths against the 512-cycle multicycle.
  Raising the gap to 1024 made it worse: −290 ns, and phys_opt ground on for hours. The
  "path" through the unconfigured routing grows with the budget, because it comes from
  where Vivado cuts the mesh's loops, not from the fabric. So:
  - the XDC's sysclk multicycle is **16384 cycles** (131 µs), far longer than any path
    through the ~4800 fabric muxes. It only tells Vivado not to optimise paths that no
    configuration has. The one-cycle exceptions on `u_clk` and `u_bram_jtag` are unchanged.
  - the default user-clock spacing is **512 cycles again** (M16–M20, proven on the board).
  - **nothing reaches the fabric untimed.** `timing.py` checks every build (the flow's
    timing stage) and every `./bob load` / studio **Program**. A design whose critical path
    × guard band is longer than its gce spacing (its `clk_gap`, or 512 when that is 0) is
    refused, stepped or free-running. The hand-written designs the board checks load
    directly are held to the same rule by `tests/test_timing.py`.
  - `clock-margin` on the board still proves the guard band on this build's measured delays.
  - **TCK too (second M21 build, 2026-09-23, `docs/reports/M21/timing.rpt`).** With
    sysclk relaxed, the build routed with **sysclk met (+0.868 ns)** and **TCK at WNS
    −463 ns** (66 endpoints). Configuration bits and the boundary/IR update cells drive the
    fabric, and CAPTURE, the boundary capture and the DSP JTAG capture sample it, all on
    TCK. The worst path: `u_tap/ir_reg[2]` (updated on the falling edge) → 6349 logic levels
    of empty fabric and DSP → `u_dsp_jtag/sr_reg[91]`, 5463 ns against the 5000 ns
    fall → rise half period. M7 had missed TCK by 657 ns the same way. TCK → TCK
    is now a 16/15 multicycle (160 µs). A configured design's pad and capture paths are tens
    of ns, and configuration bits never change while the fabric is captured.
  - **`place_report.tcl`** (a TCL.POST hook on place_design) prints the worst path of each
    clock into `runme.log` right after placement (`place_report: sysclk WNS ...`,
    `place_report: tck WNS ...`) and writes `impl_1\bob_top_timing_placed.rpt`.
- **The clock gets faster.** Logic inside a CLB reaches its neighbours through the
  crossbar, and a carry chain has no routing hop at all. `timing.py` puts M20's designs
  1.9–2.9× faster on a cluster fabric: `big` goes from 64.5 ns to 23.5 ns at N = 10, and
  it is less at N = 4.

## Size before the build

`software/bob/synth_estimate.sh` (yosys, whole design):

| | LUT | FF |
|---|---|---|
| M20 (Vivado: 20,498 LUT / 21,511 FF, WNS −0.919 ns) | 32,831 | 21,549 |
| **M21** (yosys, 2 RAMB36 for the shadow + 2 RAMB18; yosys peaked at 6.3 GB) | **58,535** | **35,995** |

At M16's ratio (Vivado 0.62 × yosys) that is about **36k LUTs, 68% of the XC7Z020**,
against M16's 38.5%. **Expect a longer implementation than M16's 3.5 h.**

- The routing mesh has more loops, so `general.maxThreads 1` stays.
- **What the timing summary should show now:** sysclk WNS ≥ 0 with the fabric paths far
  inside their 16384 cycles; the tight sysclk paths are the one-cycle ones (`u_clk`,
  `u_bram_jtag`), as at M16. phys_opt should take minutes, not hours.
- **Check the two `place_report:` lines** in `runme.log` after placement (about 15 min in).
  Both WNS should be positive. If either is negative by more than a few ns, stop the run and
  send `runme.log` and `bob_top_timing_placed.rpt`.
- If `phys_opt_design` is still logging `Estimated Timing Summary | WNS=-...` lines with a
  WNS of hundreds of ns after half an hour, **stop the run**: it will not recover. The
  same goes for a `route_design` or timer that stalls for hours. Send
  `bob_vivado\bob.runs\impl_1\runme.log`.

## Build (Windows)

1. Replace `E:\bob_full_v1\hw` with this `hw/` and run `build.tcl`.
2. Program the board, then copy the **whole** `bob_vivado\out\M21\` folder to
   `docs/reports/M21/`. It holds the timing, utilization and DRC reports, and
   `delay_paths.rpt`.
3. On the Mac:
   ```sh
   software/bob/delays.py fold docs/reports/M21/delay_paths.rpt    # the crossbar delay, measured
   make check
   ```

## Automatic (`make hwtest M=M21`), about 30 minutes

It runs the full M20 list first, on the new fabric. That means every configuration path,
partial reconfiguration, the BRAM frames, the block designs, the waveform checks and the
four clock checks. `bob-fir` must pass now. Then the new checks:

| check | pass means |
|---|---|
| shadow-readback | FDRO after a frame load == the design; **after JPROGRAM, FDRO and CHAIN_OUT read all zeros** (the shadow's valid bits); after a chain load, CHAIN_OUT == FDRO == the design |
| partial-cluster | a counter in elements 0–2 of clb(1,1) stepped to 5; a partial rewrite of element 3 (AND → OR, same CLB) keeps it at 5; 2 more clocks give 7; LD1 follows OR; FDRO == the new design |
| bob-fir16 | fir16 (16-tap FIR, 147 LUTs: it does not fit M16's 100) through VPR, stepped 64 clocks: LEDs == source, every register on CAPTURE == golden |
| pnr-fir16 | the same through bob's own pack/place/route |
| live-fir16 | fir16 on the free-running clock, LEDs == model.py on the real switches (interactive: goals below) |
| fast-fir16 | fir16 at the fastest clock its own timing allows (`--hz auto`), live against model.py |
| fmax-cluster | atspeed at the rate `timing.py` computes on the cluster fabric, the error flag stays off |

## By hand (`--manual`), about 10 minutes

- [ ] live-fir16: put SW0 up and hold **BTN0**. The delay line fills with x = 1 and the LEDs settle to a steady pattern in about two seconds (16 taps at the 7.45 Hz live clock). Release BTN0: the LEDs hold.
- [ ] Hold **BTN1**: every LED goes off (the line clears).
- [ ] SW0 and SW1 up, BTN2 and BTN0 held together (x = 7): the LEDs settle to a different pattern than for x = 1.
- [ ] In the studio (`./bob studio --probe usb`), open `work/examples/fir16/fir16.v` and **Generate Bitstream**. The Device view shows the CLBs used, each with its **four element cells**; fractured ones are drawn half-filled. Hover a CLB: the tooltip names each element's mode.
- [ ] `./bob build work/examples/big/big.v --clock run --hz auto -o build/bit/big.bit`: the timing line shows the critical path. It should be well under M20's 64.5 ns for `big`.
