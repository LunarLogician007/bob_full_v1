# M20 hardware test: a per-design user clock

**This milestone needs a Vivado rebuild.** `hw/build.cfg`:
- `tag = M20`
- `top = bob_top`
- `idcode = 0B020093`: the new IDCODE scheme. The version nibbles ran out at M16 (`0xF`), so
  the version is now 0 and the 16-bit part field names the milestone in readable digits:
  `0B0 20` is M20, `0B0 21` will be M21.
- `usercode = 00000014` (20)
- `delays = 1`: the new measurement step (below). `delays = 0` skips it.

## What changed

**The user clock.** Until now it was at most 244 kHz, because `clock_ctrl.v` kept gce pulses
at least 512 sysclk cycles apart. That number covers the worst path through the *unconfigured*
fabric (about 2500 ns at 12 × 10), which is the only thing Vivado can time. A configured
design's own paths are far shorter. FPGA overlays sign off the design, not the empty fabric:
- ZUMA, Brant & Lemieux, FCCM 2012
- "Timing Optimization for Virtual FPGA Configurations", ARC 2021

bob now does the same:

| | before | M20 |
|---|---|---|
| free-running rate | 125 MHz / 2^(div+9), at most 244 kHz | 125 MHz / (`clk_period` × 2^`clk_div`), any integer period |
| gce spacing | always ≥ 512 cycles | the design's own `clk_gap` (≥ 2 cycles, 62.5 MHz), from its critical path |
| unconfigured / old `.bit` | 512 | **unchanged: `clk_gap` = 0 means 512** |
| XDC | multicycle 512 / 511 | **unchanged**: it still describes the empty fabric, and Vivado never chases it |

- `software/bob/timing.py` times the configured design from its bits. It follows only the
  selected mux inputs and the LUT inputs the truth table uses, and times register-to-register
  paths only. The switches and LEDs are asynchronous and false-pathed.
- **The clock is a constraint, as in Vivado:** a `.sdc` with `create_clock -period <ns>
  [get_ports clk]`. It goes in the project's `constrs/` (the studio's **Create clock
  constraint…**), or `./bob build --sdc file.sdc`. The build reports the slack; **a negative
  slack fails the build and writes no `.bit`**, naming the path and the fastest clock the
  design can make. `--hz N` is the same check without a file; `--hz auto` picks the fastest
  safe clock.
- The element delays come from `software/bob/delays.json`. Until this build it holds
  **provisional** routing delays: 702 channel hops and 12 input hops measured on M16's timing
  report, worst 3.61 ns, median 1.68 ns. LUT, flip-flop, BRAM and DSP delays are estimates.
  Provisional delays carry a **2×** guard band and measured ones 1.25×.

**The delay measurement.** After implementation, `hw/scripts/extract_delays.tcl` times 624
samples of every element class listed in `hw/scripts/delay_samples.txt`: routing mux, input
mux, LUT, carry, and flip-flop clock-to-Q and input-to-D. It writes them to
`out/M20/delay_paths.rpt`. It only reads timing and never changes the design.

**The readback mux, measured and left alone.** HANDOFF §5 expected a restructured frame
read mux to save most of `cfg_store`. Measured on `cfg_store` alone, a balanced tree does beat
the flat array. In the whole design it does not: flattening lets yosys fold the flat array
into the FDRO word select that follows it, and the tree prevents that.

| `cfg_store` readback | LUTs (yosys) |
|---|---|
| alone, flat 256-entry array | about 12,400 |
| alone, balanced tree | about 9,200 (about 5,600 with MUXF7/F8) |
| **whole design, flat array** (M16's code, kept) | **32,838** |
| whole design, tree | 33,148 (**+310**) |

So `cfg_store.v` keeps M16's code, which Vivado has already built and the board has already
passed. The floor for any mux over the 18,560 configuration bits is about 4,600 LUTs. Making
real room for M21's cluster needs a different memory (a BRAM shadow for readback, or ZUMA's
LUTRAM), not a different mux.

## Size before the build

`software/bob/synth_estimate.sh` (yosys, whole design), against the last build:

| | LUT | FF |
|---|---|---|
| M16 (Vivado built it: 20 498 LUT / 21 511 FF, WNS +0.667 ns) | 32 891 | 21 485 |
| **M20** | **32 831** | **21 549** |

Within a few LUTs of M16, and 64 more flip-flops: the two 16-bit ctrl fields and their
synchronisers. Vivado should land near M16's 20 498 LUT / 21 511 FF, so this build carries
no more risk than M16's did.

## Build (Windows)

1. Replace `E:\bob_full_v1\hw` with this `hw/` and run `build.tcl`.
   - The delay measurement runs after the bitstream is written. It prints
     `extract_delays: N samples ...` every 100. Expect 10–40 minutes for 624 samples: the
     fabric is loop-ridden, so each `report_timing` is slow. If it runs far longer, stop it:
     the bitstream is already in `out/M20/`. Then rebuild with `delays = 0` and send the log.
2. Program the board. Copy the **whole** `bob_vivado\out\M20\` folder to `docs/reports/M20/`,
   including `delay_paths.rpt`.
3. On the Mac:
   ```sh
   software/bob/delays.py fold docs/reports/M20/delay_paths.rpt    # delays.json: measured
   make check
   ```
   The fold prints each class's count, worst, 95th percentile and median. Classes the sample
   missed keep their provisional values, and the file says which.
4. If Vivado stops or the PC restarts, send `bob_vivado\bob.runs\impl_1\runme.log`.

## Automatic (`make hwtest M=M20`), about 20 minutes

The full M19 list first: the whole regression on the new bitstream, including idcode
`0x0B020093`, both configuration paths, partial reconfiguration, the BRAM frames, the block
designs and the waveform checks. Then:

| check | pass means |
|---|---|
| clock-rate | blinky at `clk_period` 47 × 2^16 (40.6 Hz, not a power of two) counts at that rate within 10%, by CAPTURE over about 4 s |
| clock-fmax | `atspeed` runs at the rate `timing.py` computed from its critical path (VPR route). A counter checks itself against its last value every clock, and after 1 s its sticky error flag (LD0) is still off and the registers are moving |
| clock-fmax-py | the same through bob's own place and route |
| clock-margin | `atspeed` again, from the computed clock up to the 2-cycle floor (62.5 MHz), one rate at a time, until the error flag latches. **Every rate up to the computed one must pass.** The first failing rate is printed as the guard band measured on silicon: "margin 1.8x" means the design broke at 1.8 times the rate it is given |

`clock-margin` is the check that proves the method. If it fails, the delays are too small:
send the output and `delay_paths.rpt`.

## By hand (`--manual`), about 5 minutes

- [ ] `./bob build work/examples/atspeed/atspeed.v --clock run --hz auto -o build/bit/atspeed.bit`: the **timing** line prints a critical path in ns and a rate in MHz, and the bit is written. Then `./bob load build/bit/atspeed.bit --probe usb`: **LD0 stays off** (no error), while LD1 and LD2 (the counter's top bits, toggling at kHz) look dimly lit
- [ ] Press and release **BTN1** (clear): LD0 stays off, LD1 and LD2 keep flickering
- [ ] `./bob build work/examples/atspeed/atspeed.v --clock run --hz 60e6 -o build/bit/too_fast.bit` **fails**: "timing not met ... slack −N ns", naming the path and "the fastest this design can run", and no `.bit` is written
- [ ] Clock constraint in the studio: **New Project…** (anywhere), add `work/examples/counter/counter.v`, set it as top, set **pnr → python**. **Create clock constraint… → 5 MHz**, then **Generate Bitstream**: Timing is green and Utilization shows **slack +… ns (met)**. **Create clock constraint… → 60 MHz**, Generate Bitstream again: the Timing row turns **red**, the slack reads **(FAILED)**, the log says "timing not met", and no new `.bit` appears in the project's Outputs
- [ ] In the studio (`./bob studio --probe usb`), open `work/examples/counter/counter.v`. In the right panel set **clock → run** and **hz → auto**, then **Generate Bitstream**. The Flow Navigator's **Timing** row turns green; Utilization shows the critical path, **Fmax**, and the user clock in MHz. **Program Device**, then **hold BTN0** (counter.v counts only while it is held): LD0–LD2 (q[5:3]) flicker too fast to follow, where a `--div` build counts visibly. Release BTN0 and they hold still
