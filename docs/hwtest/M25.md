# M25 hardware test: time-travel debugging, and TCK at 1 MHz

**This milestone needs a Vivado rebuild.** `hw/build.cfg`:
- `tag = M25`
- `top = bob_top`
- `idcode = 0B025093`
- `usercode = 00000019` (25)
- `delays = 1`

## What changed

**Time-travel debugging** (after Attia & Betz, *Toward Software-like Debugging for FPGAs via
Checkpointing and Transaction-based Co-Simulation*, TRETS 2022):

- **Capture:** freeze the running design (UG470 AGHIGH) and read every flip-flop it uses
  through CAPTURE.
- **Restore:** one partial stream (`packets.restore_streams`) in five steps:
  1. The CLB frames, with each used flip-flop's INIT bit set to the snapshot.
  2. **UG470 GRESTORE** (CMD 10, new in `cfg_frames.v`): the fabric's GSR pulses, and every
     flip-flop takes its INIT value.
  3. The original frames back.
  4. The state is read back through CAPTURE while still frozen.
  5. One CRC over the whole stream, then LFRM releases the freeze.

  GRESTORE is refused (WR_ERROR) unless the fabric is frozen or not yet started.
- **Simulator hand-off:** a snapshot becomes `model.py`'s state and back, so a design
  running on the board can be moved into the simulator, stepped there, and pushed back
  onto the chip.
- **`bob snap save|restore|list|sim NAME`** (`software/bob/cli.py`),
  `software/host/snapshot.py`.
- **Limits:** a snapshot holds the CLB flip-flops. BRAM contents stay as they are.
  GRESTORE resets BRAM output registers and DSP pipeline registers, as AMD's does, and
  `snapshot()` names them for a design that uses them.

**TCK constrained at 1 MHz** (was 10 µs). The long TCK path Vivado sees runs through the
*empty* mesh (5.46 µs at M21) and never carries a change. It fits the 16-period multicycle.
A configured design's paths are tens of ns. The probe default stays 100 kHz until
`fast-tck` passes on the board.

## Watch in runme.log

- Both `place_report:` lines: WNS must be positive for sysclk and for tck. At 1 MHz, TCK's
  budget with the multicycle is 16 µs.
- If TCK fails timing, send `runme.log` and `timing.rpt`. The fallback is
  `XDC_TCK_PERIOD_NS = 10000` in `device.py` and the XDC; the time-travel part is
  unaffected.

## Build (Windows)

1. Replace `E:\bob_full_v1\hw` with this `hw/` (from the `bob_full_v1_m25` worktree) and
   run `build.tcl`.
2. Program the board. Copy **the files** of `bob_vivado\out\M25\` (not the folder) into
   `docs/reports/M25/`, including `delay_paths.rpt`.

## Automatic (`make hwtest M=M25`), about 12 minutes

The full M24 list runs first. Then:

| check | pass means |
|---|---|
| time-travel | Counter (JTAG-stepped): step to 5 and snapshot; run on to 11; restore, and it reads 5 again; +3 → 8. Then that state into `model.py`, +4 there, pushed back onto the chip (12), one board step → 13. |
| fast-tck | Every self-test design loaded as frames (CRC, FDRO readback) and swept against the model at 100 kHz and at **1 MHz**, then time-travel again at 1 MHz; reports the speed-up. |

## By hand (`--manual`), about 5 minutes

- [ ] `./bob build work/examples/blinky/blinky.v --clock run --div 13 -o build/bit/blinky_run.bit`, then `./bob load build/bit/blinky_run.bit`: LD2..LD0 count in binary, LD0 toggling about every 0.54 s.
- [ ] `./bob snap save a`, note the LED pattern, wait about 5 seconds, then `./bob snap restore a`: the LEDs jump back to the saved pattern and count on from there.
- [ ] `./bob snap sim a --steps 64 --save b`, then `./bob snap restore b`: the LEDs show the counter 64 user-clock steps after `a` (blinky counts on its own clock, no `--cin` needed), computed by the simulator.
