# M13 hardware test: frame-based configuration next to the chain, and M7's timing fixed

**This milestone needs a Vivado rebuild.** `hw/build.cfg`:
- `tag = M13`
- `top = bob_top`
- `idcode = BBEEF093`
- `usercode = 0000000D`

## What changed

### 1. Frames, like AMD 7-series (docs/bitstream-format.md sections 9–10)

**Memory layout:**
- The configuration memory is laid out in **frames of 4 × 32-bit words (128 bits)**, column by column: FAR column 0 is the ctrl tile, FAR column x+1 is grid column x.
- There are 39 frames, so the memory is 4992 bits. It was 4216; each column is now padded to whole frames.
- The chain is exactly all frames end to end, so one chain word loads identically either way.

**CFG_IN / CFG_OUT now carry UG470-style packets:**
- sync word `0xAA995566`
- type-1 and type-2 headers
- registers CRC, FAR, FDRI, FDRO, CMD, STAT, IDCODE
- CMD verbs WCFG, RCFG, RCRC, LFRM, START, DESYNC
- CRC-32C over `{register, data}`
- FAR auto-increment

**Simplifications against 7-series:**
- a frame lands the moment its 4th word arrives: no trailing pad frame, no leading garbage frame on readback
- no encryption, compression or bus-width detection
- BRAM contents stay on USER4 (FAR block type 001 is reserved for them)

**The scan chain is kept:** it moved to the private instructions `CHAIN_IN` (`110101`) and `CHAIN_OUT` (`110100`), with CFG_CTRL and its CRC and length guard unchanged. Both paths refuse writes while GWE = 1.

**On the Mac:**
- `bob load x.bit` uses frames by default; `bob load --mode chain` uses the chain.
- `software/bob/packets.py dump x.bit` prints the packet stream.

### 2. M7's timing (WNS −1102 ns, TNS −1 608 726 ns, 1858 failing endpoints)

Two real causes were found in `docs/reports/M7/timing.rpt`:

| cause | M7 path | fix |
|---|---|---|
| **sysclk:** fabric register → 1202 logic levels through unconfigured routing loops → BRAM, 1110 ns | synthesis flattened and renamed the source (`hold_qb_reg[17]_i_5__0`, outside any `u_bram*/u_core` name), so the 120-cycle multicycle missed it; and 120 cycles = 960 ns would be too short anyway | `clock_ctrl.v` now **guarantees** user-clock enables ≥ 256 sysclk cycles apart in both clock modes (`tb_clock_gap.v`); one 256-cycle (2048 ns) multicycle over sysclk → sysclk, by clock; `u_clk` and `u_bram_jtag` (kept hierarchies) held to one cycle by name |
| **tck:** IR / boundary update → fabric → DSP JTAG capture register, ~1650 ns under a 1000 ns clock | a real TCK-to-TCK path; TCK was constrained at 1 MHz but is driven at 100 kHz | TCK constrained at 10 µs (100 kHz); `software/host/dirtyjtag.py` refuses a faster TCK |

**Rule added:** on both paths, configuration changes only while GWE = 0, i.e. before startup. So the asynchronous TCK → sysclk crossing never changes bits the running fabric is sampling.

## Proofs before the build (`make check`, `make mutate`)

- **`sim/run_frames_sim.sh`:**
  - **`tb_frames`, 34 checks:** every expected value comes from `packets.Controller`, the Python model of the controller, not from the RTL. Scenarios:
    - a good frame load: STAT, memory, CHAIN_OUT readback, DONE, LEDs
    - FDRO readback of every frame
    - garbage before sync, with the stream split over three scans
    - a flipped frame bit (CRC_ERROR, no DONE)
    - a wrong IDCODE
    - frames while running refused
    - packet error
    - FDRI without WCFG
    - the chain after frames
    - a chain while running refused
    - no CRC write (START refused)
    - FDRO without RCFG
  - **`tb_clock_gap`, 5 checks:** fast steps are spaced at least 2^GAP cycles apart, slow steps are unchanged, free-running spacing is exact.
- **Earlier testbenches:** `tb_bob` (852), `tb_cfg` (180), `tb_synth` (972), `tb_cosim` (4618) and the K=4 run all pass on the new layout, with the chain on CHAIN_IN/CHAIN_OUT.
- **`sim/mutate_frames.sh`:** 17 mutants, all killed. Each one breaks a guard (the 17th drops the frame load into the shift register):
  - the CRC compare, and CRC covering data only
  - the IDCODE check
  - GWE, WCFG
  - FAR auto-increment
  - START needing CRC_OK
  - type-2 without type-1
  - FDRO needing RCFG
  - the sync word
  - readback bit order
  - chain commit while running
  - startup via frames
  - the frame write itself
  - the gce gap, and the pending step
- **`tests/test_hwtest_fake.py`:** every new board check passes on the stand-in board, which now models the frame controller. Boards that write while running or ignore the CRC make the checks fail.
- **`tests/test_reports.py`:** from M13, `timing.rpt` must show WNS ≥ 0, 0 failing endpoints and WHS ≥ 0, and the logs must have no "No valid object" warning.

## First build attempt (2026-09-17): Vivado closed during synthesis

The first M13 RTL wrote a frame with `cfg[frame_idx*128 +: 128] <= frame_data` over the whole 4992-bit memory. That line synthesises as a shifter.
- **The frame write alone:** in yosys it cost ~12 300 LUTs and 2 300 MUXF7/8, and 1.7 GB of memory. Vivado ran out of memory and exited.
- **The fix:** a frame now goes into the chain's shift register (don't-care outside CHAIN scans). It is copied into the memory with a per-frame enable, the same path the chain commit uses, so no memory bit needs a LUT.
- **The FDRO readback:** it is now an explicit word array instead of a computed part-select.

yosys estimates for the whole `bob_top` (`synth_xilinx -flatten`; not Vivado, but the trend):

| | LUTs | FFs | yosys time | peak memory |
|---|---|---|---|---|
| M7 RTL | 11 349 | 10 375 | 138 s | 1.40 GB |
| M13 now | 15 146 | 12 218 | 152 s | 1.42 GB |

The remaining +3.8k LUTs are the FDRO readback mux (~1.7k), the packet controller (~0.9k) and the 776 frame-padding bits in the shift register.

## Second build attempt (2026-09-17): Vivado closed again, same place every time

`runme.log` holds three runs. Each one:
- passed RTL optimisation, Cross Boundary Optimization and Applying XDC Timing Constraints (peak memory 1977 MB, about what M7 used)
- then died while breaking the fabric's timing loops, after exactly 47 `Synth 8-326` messages, before Technology Mapping

M7 got through the same loops (51 045 "Found timing loop" reports) and finished. What M13 changed at that point: `keep_hierarchy` on `u_fabric`. Vivado then broke the loops with `set_disable_timing` on the kept boundary (M7: `set_false_path -through` on the flattened netlist). Loop breaking and the fabric-name multicycles both run in this phase.

**The fix:**
- `u_fabric` is flattened again, as at M7.
- The 256-cycle multicycle is now by clock (sysclk → sysclk), so it doesn't depend on fabric cell names.
- The only sysclk logic outside the fabric is `u_clk` and the sysclk half of `u_bram_jtag`. Both are small and loop-free, keep their hierarchy, and are held to one cycle by cell name (cell exceptions take precedence over clock exceptions, UG903).
- The cin synchroniser keeps its 256 cycles into the fabric, as before.

## Third build attempt (2026-09-17): same crash

The new log died at the same place (48 `Synth 8-326`, before Technology Mapping). The instance names still show a `u_corei_2/` partition, which M7's log never has, and Vivado still broke the loops with `set_disable_timing`. So `keep_hierarchy` on `u_clk` and `u_bram_jtag` was enough to keep `u_core` from flattening into the top. M7 had no `keep_hierarchy` anywhere.

**The fix:**
- `bob_fpga.v` now has no `keep_hierarchy` at all, as at M7.
- The XDC is unchanged: 256 cycles by clock, and `u_clk` / `u_bram_jtag` held to one cycle by name (those names survived flattening at M7, e.g. `u_core/u_clk/cnt_reg`).
- `build.tcl` writes `out\M13\sysclk_1cycle.txt`, the registers that filter caught. `make check` fails if `u_clk/gce_reg`, `u_bram_jtag/init_go_reg` or `u_bram_jtag/rdata_reg` is missing from it.

## Fourth build attempt (2026-09-17): same step, and Windows restarted

The run used the new RTL (its cell names differ from the 11:46 run), still went into the same partition (`u_corei_2`), and stopped at the same step. This time the whole PC restarted.

A program crash alone does not restart Windows. It points at the machine under load: running out of memory, overheating, or power/RAM trouble. The one constant is the step: synthesis applies the XDC clocks, then breaks the fabric's routing loops against them.

**The fix:** `build.tcl` sets `USED_IN_SYNTHESIS false` on the XDC, so synthesis runs without clocks. Nothing is lost:
- Synthesis uses `RuntimeOptimized`, and the fabric is multicycle by construction.
- Implementation still reads every pin, IOSTANDARD and timing constraint, and `timing.rpt` must still close.

If Vivado still exits, send `E:\bob_full_v1\bob_vivado\bob.runs\synth_1\runme.log` and any `hs_err_pid*.log` from `E:\bob_full_v1\bob_vivado\`.

## Build (Windows)

1. Replace `E:\bob_full_v1\hw` with this `hw/` and run `build.tcl`. The sources changed, so it rebuilds; new files `cfg_store.v` and `cfg_frames.v` are added from `sources.f`.
2. Program the board and copy `bob_vivado\out\M13\` to `docs/reports/M13/`.
3. Run `make check` on the Mac. It now requires timing to close. If it doesn't, send `timing.rpt`: a failing path now points at something new rather than the known loop artefacts.
4. Look at `util.rpt`. M7 had 7670 LUTs and 10362 FFs. Expect roughly +2k FFs and +4k LUTs (the frame controller, the FDRO readback mux, and 776 padding bits in the shift register; from the yosys estimate above). Area is deferred (M12b).

## Automatic (`make hwtest M=M13`)

The regression runs first: `idcode` (`0xBBEEF093`), `bypass`, `selftest`.

**All M7 fabric checks, through the chain:**
- usercode (13), chain-length (4992), ir-status, crc-reject-live, gts, gsr-gwe, capture-user1, jprogram, showcase-live
- ce-sr, counter-step, counter-run
- bram-init, bram-locked, bram-rom, bram-modes, bram-select
- dsp-modes, dsp-mult, dsp-accum
- pipeline, counter8

**Then the frame path:**

| check | pass means |
|---|---|
| frames-load | showcase via CFG_IN packets: STAT has START accepted and no error; FDRO readback == chain word; CHAIN_OUT readback of the same memory == chain word; JSTART → DONE; LEDs == model |
| frames-crc-reject | one flipped frame-data bit: STAT CRC_ERROR, START not accepted, DONE never rises, IR capture INIT_B low |
| frames-idcode-reject | a stream for another IDCODE: ID_ERROR, no frame written |
| frames-live-refused | while showcase runs: a frame load of another design gives WR_ERROR, and a good chain does not commit either; memory unchanged, DONE still up, showcase LEDs == model |
| frames-vs-chain | a chain load reads back identically through FDRO, and a frame load through CHAIN_OUT |

**Then guest designs, which `bob load` now sends as frames:**
- bob-gates, bob-counter, bob-ram, bob-mult, bob-fir, each with LEDs == source and CAPTURE == golden
- pnr-switches (Python-routed)
- ram-readback (BRAM read after JPROGRAM)
- blinky-rate (still 14.9 Hz: the gce guard doesn't slow the free-running clock)
- pipeline-live runs last and leaves the pipeline on the switches
