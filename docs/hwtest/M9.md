# M9 hardware test: VPR packs, places and routes the examples

No RTL change and **no Vivado rebuild**: the M7 bitstream (`bob_top`, IDCODE `0xABEEF093`, 4216-bit chain) stays in the PL. `hw/build.cfg` stays tagged M7; `hwtest` prints a note about that.

Why no rebuild is needed:
- M9 changed only the *inside* of VPR's CLB (the pb_type modes VPR packs into). Tile pins, fc, switch blocks and segments are unchanged.
- `make rrgraph` was rerun, and both routing-resource graphs (K=6 and K=4) came out **byte-identical** to the committed M7 ones. `device.json`, `bob_params.vh` and `bob_fabric.v` are all "up to date".
- Every route VPR finds is therefore a path through muxes the programmed bitstream already has.

## The flow

1. `software/bob/equiv.py`: yosys synthesis onto bob cells; the netlist equals the source in iverilog (as M8).
2. `software/bob/vpr_run.py` (Docker, `make vpr`) prepares the netlist for VPR, then runs VPR:
   - writes `<top>.eblif` from the yosys JSON:
     - constants on pins become IPIN constants
     - carry chains are cut to the 4-row column with generator/tap CLBs
     - `BOB_FDRE`/`BOB_FDSE` become `bob_ff`
     - an FF D that is not its own CLB's LUT/adder output gets a buffer LUT
   - fixes the board pins
   - runs VPR 9 (OpenFPGA image) with `--read_rr_graph` on the committed graph and a fixed seed
   - results are committed in `software/bob/vpr/<top>/` (`.eblif .pins .vpr.json .net .place .route stamp.txt`)
3. `software/bob/fasm_from_vpr.py` (no Docker) turns the committed result into chain bits:
   - `.net`/`.place`/`.route` → FASM (`clb_x2y3.init = 64'h…`, `rr1234 = 3'h5`)
   - checks every feature against `device.json`
   - builds the chain
   - refuses a result routed from a different netlist or architecture
4. Checks, before the board:
   - `model.py` == source trace, all 300 cycles before and after each edge
   - `tb_synth` runs the same chains on the complete FPGA RTL

| example | CLBs (of 16) | hard blocks | generators / taps / FF buffers | wirelength | VPR critical path* |
|---|---|---|---|---|---|
| gates | 3 | | | 108 | 1.60 ns |
| adder | 4 | | 1 / 0 / 0 | 59 | 1.74 ns |
| counter | 11 | | 3 / 2 / 0 | 182 | 3.62 ns |
| blinky | 15 | | 4 / 3 / 0 | 144 | 4.85 ns |
| ram | 0 | 1 BRAM | | 99 | 1.58 ns |
| mult | 7 | 1 DSP | 0 / 0 / 7 | 157 | 1.81 ns |

\* VPR's timing uses the reference architecture's 40 nm delay numbers. It is not the speed of the emulated fabric on the XC7Z020, which is set by the host's routing-loop paths (M7 timing notes). The DSP model is marked clocked, but bob's opmode M is combinational.

Same seed, same result: `make vpr` routes each example twice and compares the result hashes (`--repeat`).

## Automatic (`make hwtest M=M9`)

The regression runs first: `idcode` (`0xABEEF093`), `bypass`, `selftest`, then `chain-length` (4216).

Each `vpr-*` check:
1. re-synthesises the example and checks the committed VPR result is still fresh
2. builds the chain from it and loads the chain
3. writes any BRAM contents over USER4, then runs JSTART
4. clocks once per INTEST scan (USER1 autostep), for 64 clocks
5. requires the LEDs after every clock to equal the source Verilog's

| check | example |
|---|---|
| vpr-gates | AND, 6-input parity, mux: 3 LUTs, VPR's own LUT pin permutation |
| vpr-adder | `sw + btn[1:0]`: carry chain placed by VPR as a macro |
| vpr-counter | 6-bit counter, CE BTN0, sync reset BTN1: chain over 3 columns, CE/SR routed to FF pins |
| vpr-blinky | 8-bit free counter: 15 of the 16 CLBs |
| vpr-ram | inferred BRAM, contents over USER4; VPR chose the BRAM site |
| vpr-mult | registered multiplier on a DSP slice; inputs registered through buffer LUTs |

Stimulus note: the source traces now use biased random vectors (`equiv.py`). The M8 `counter` trace had all LEDs at 0 for all 300 cycles, because reset was asserted half the time, so M8's counter check could not fail. The new traces reach LED values 0–6 on the counter.
