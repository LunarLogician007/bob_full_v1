# M16 hardware test: the 10 × 10 CLB grid

**This milestone needs a Vivado rebuild.** `hw/build.cfg`:
- `tag = M16`
- `top = bob_top`
- `idcode = FBEEF093`  (the last free IDCODE version nibble)
- `usercode = 00000010`

## What changed

Only the device description changed: `software/bob/device.py` `ARCH_12X10` replaces `ARCH_8X6`. Everything else — the configuration plane, both configuration paths, partial reconfiguration, BRAM content frames, the tools — is the M15 design, regenerated for the bigger grid.

| | M15 (on the board now) | M16 |
|---|---|---|
| VPR grid (with the I/O ring) | 10 × 8 | **14 × 12** |
| core | 8 × 6 | **12 × 10** |
| CLBs | 36 | **100** |
| BRAM / DSP | 2 / 2 (height 3) | 2 / 2 (height 5, columns x = 3 and x = 8) |
| pads | 28 | **44** |
| routing muxes | 1723 | **3391** |
| configuration | 8320 bits = 65 frames | **18 560 bits = 145 frames** |
| K = 4 profile | 6016 = 47 frames | 12 800 = 100 frames |
| boundary cells | 56 | 88 |
| gce gap = XDC multicycle | 256 cycles (2048 ns) | **512 cycles (4096 ns)** |
| free-running guest clock | ≤ 488 kHz | **≤ 244 kHz** |

**Size, measured before the build** (`software/bob/synth_estimate.sh`, whole design, yosys):

| | LUT | FF | yosys time | yosys peak |
|---|---|---|---|---|
| M15 (Vivado built it: 5.1 min at 2.0 GB → 10 411 LUT / 11 097 FF, WNS +0.585 ns) | 15 941 | 11 069 | 152 s | 1.36 GB |
| **M16** | **32 891** | **21 485** | 281 s | 2.07 GB |

Scaling by M15's yosys → Vivado ratio, expect roughly **21 k LUTs (≈ 40% of the XC7Z020)** and **≈ 21.5 k FFs (≈ 20%)**. That fits, but this is the first build where synthesis is clearly bigger than M15's five minutes, and the loop-breaking phase grows with the routing muxes (1723 → 3391).

**If the machine struggles** (it restarted once under load at M13): say so and we drop to an 8 × 8 core (64 CLBs), which is about half this growth. Close other programs first; `jobs = 1` in `hw/build.cfg` makes implementation gentler.

The rules that made M13 and M15 build are unchanged: no computed part-select over the configuration memory, no `keep_hierarchy`, and the XDC is used in implementation only.

## New example: `work/examples/big/big.v`

A 24-bit LFSR and a 16-bit counter, **56 CLBs** — it cannot fit the 36-CLB grid at all. BTN0 steps both, BTN1 resets them, and the LEDs mix the parity of the LFSR, the parity of the counter and the two switches, so every register reaches an output. It goes through the same checks as every other example: yosys equivalence (300 cycles), VPR and bob's PnR, FASM legality, `model.py` against the source trace, golden co-simulation, and on the board LEDs == source with CAPTURE == golden.

## Proofs before the build (`make check`, `make mutate`)

- Every testbench passes on the 100-CLB fabric: `tb_bob` 852, `tb_frames` 71, `tb_clock_gap` 11, `tb_cfg` 180, `tb_synth` 972, `tb_cosim` (now 11 designs × 2 flows), `tb_clb`/`tb_bram`/`tb_dsp`, and the K = 4 fabric.
- VPR routes all 11 examples on the new graph; bob's PnR does too (`make pnr`).
- All three mutation suites pass. `sim/mutate_fabric.sh`'s `carry-direct-cut` now cuts the carry of **column 12** (the last CLB column, `designs.FULL_COL_X`).
- Fixed while resizing (real bugs, not just numbers):
  - `tb_bob` used `` `CNT8_BITS `` above the `include` of `vectors.vh`: iverilog did not complain and the comparison register came out 2 bits wide, failing 298 checks. The comparison registers are plain 32-bit now.
  - The CAPTURE check compared 64-bit values; CAPTURE is 100 bits on this grid.
  - `CNT8_MASK` carried a fixed `8'h` width; it now matches the column height (10 bits).
  - The frame testbench's stream vector (16 384 bits) was too small for a 145-frame load stream; `SW` is 40 960 in `sim/gen_frame_vectors.py` and `hw/tb/tb_frames.v` (they must match).
  - `test_blinky_chain_crosses_columns` proved the M8 placer splits a carry chain across columns. With 10-row columns blinky fits one column, so the test uses `wide` and also checks each piece occupies contiguous rows.

## The 2026-09-18 attempt, and what changed for the rebuild

The first Vivado run **passed synthesis and then ran 3 h 25 min in implementation without
finishing**. It was not a machine problem and not a tool setting:

| step | elapsed |
|---|---|
| `opt_design` | 1:22 |
| `place_design` | 14:28 |
| `phys_opt_design` | **1:15:18** (started at WNS −465.7 ns, recovered 128 ns) |
| `route_design` | 57:51 at the end of global iteration 1, iteration 2 still running |

`phys_opt_design` reported **WNS −465.7 ns / TNS −333 768 ns** on fabric flop → flop paths
(`u_core/u_fabric/u_clb_x11y6/q_reg/D` and friends), and the router then printed
`WARNING: [Route 35-447] Congestion is preventing the router from routing all nets. The
router will prioritize the successful completion of routing all nets over timing
optimizations` with WNS ≈ −337 ns and overlaps growing every global iteration
(25 551 → 30 325 → 34 608).

**Cause:** the fabric's flop-to-flop budget is `set_multicycle_path -setup 256` × 8 ns =
**2048 ns**, true only because `clock_ctrl.v` guarantees gce pulses ≥ 256 sysclk cycles
apart. M15's 8 × 6 fabric fitted in it; the static path through the 12 × 10 fabric's
unconfigured routing muxes is about **2500 ns**, so thousands of endpoints failed by
300–470 ns and both phys_opt and the router were chasing something unreachable.

**Fix (in this bundle):**

- `software/bob/device.py`: `DIV_MIN_SHIFT` = `GCE_MIN_GAP_SHIFT` = **9** → gce pulses ≥ **512
  sysclk cycles = 4096 ns** in both clock modes (`clock_ctrl.v`, `tb_clock_gap`), about 63 %
  headroom over the 2500 ns the fabric needs.
- `hw/constr/pynq_z2.xdc`: `set_multicycle_path -setup 512 / -hold 511` on sysclk → sysclk.
  The RTL guarantee and the constraint must always be the same number.
- `hw/scripts/build.tcl`: `STEPS.PHYS_OPT_DESIGN.IS_ENABLED **true**` on `impl_1`, set
  explicitly because Vivado stores it in the project. It was briefly turned off (with the
  old gap it burned 1 h 15 min for 128 ns), but `route_design` then died inside "Phase 2.3
  Update Timing" with no message, and the only implementation that ever got through that
  phase on this fabric had phys_opt in the flow. With the gap right it has nothing to fix
  and costs seconds.
- `software/host/hwtest.py`: `counter-run` and `dsp-accum` derived their expected rate from a
  hard-coded number; they now compute it from `DIV_MIN_SHIFT` (every free-running rate
  halves with this change).

**What it costs:** the free-running guest clock halves — **244 kHz maximum** instead of
488 kHz, so every `--clock run` design runs at half its old rate (`--div 17` is 1.9 steps/s,
not 3.7). JTAG-stepped mode is unchanged: TCK at 100 kHz asks for a step every 10 µs, still
slower than the 4.1 µs gap.

## The second attempt (2026-09-18 10:59): the gap fix worked, the router crashed

With the 512-cycle gap the whole front of the flow came right:

| | attempt 1 (256 cycles) | attempt 2 (512 cycles) |
|---|---|---|
| post-place WNS | −465.7 ns | **+0.531 ns** (`[Place 30-746]`) |
| `place_design` | 14:28 | **6:26** |
| `phys_opt_design` | 1:15:18 | skipped (it was disabled for this run) |
| post-place congestion (global) | East **32 × 32**, S/W 16 × 16 | N 4 × 4, S 2 × 2, E 4 × 4, W 8 × 8 |

Then `route_design` **died inside "Phase 2.3 Update Timing"** — the log stops mid-phase with
no `ERROR:` line and without the closing `Phase 2.3 … | Checksum`, and the GUI shows only
`[Vivado 12-13638] Failed runs(s) : 'impl_1'`. That is the implementation process being
killed, not a routing failure: `launch_runs` runs impl_1 as a separate process, so the GUI
survives it. Memory at the last logged point was 2.2 GB (attempt 1 reached 2.4 GB and
survived), so it does not look like the machine running out of memory.

Update Timing is where the timer rebuilds the graph over the fabric's combinational routing
loops — the same component that killed three M13 synthesis runs (that one was fixed by
taking the XDC out of synthesis; implementation cannot do without it). The 12 × 10 fabric
has about 2.7× M15's independent cycles.

**Found it: two threads crash the timing engine.** Run by hand from the placed checkpoint,
`phys_opt_design` + `route_design` took Vivado itself down (interactive, so the crash is in
the main process rather than a child). With

```tcl
set_param general.maxThreads 1
```

the *same checkpoint* routes through. It is a threading fault, not a property of the design:
the timer has to cut every combinational loop in the routing mesh — M16 has one strongly
connected component of **2146 routing wires with 11 270 independent cycles**, against M15's
1018 wires / 4130 cycles — and two threads doing that concurrently is what falls over. It
also explains M13: three synthesis crashes at the equivalent phase, on a smaller version of
the same mesh.

**In the flow now:** `hw/scripts/drc_waiver.tcl` (the implementation TCL.PRE hook) sets
`general.maxThreads 1`, and `build.tcl` hooks it on `opt_design`, `route_design` and
`write_bitstream`. It has to live there and not in the calling session: `launch_runs` starts
implementation as a **separate process**, so a `set_param` typed in the GUI console never
reaches it. `phys_opt_design` is back on as well (explicitly `true` — Vivado stores that
property in the project, so the run that turned it off would have kept it off).

The cost is wall-clock only: roughly 1.3–1.7× on implementation (7-series caps these commands
at 2 threads anyway). Worth retesting on a later Vivado.

The **8 × 8 fallback below was not needed.**

Note for a manual `write_bitstream` from a checkpoint: `drc_waiver.tcl` keys off the
project's top property, which an `open_checkpoint` session does not have, so downgrade the
check by hand first — `set_property SEVERITY {Warning} [get_drc_checks LUTLP-1]`.

**Optional 5-minute confirmation before the full rebuild** — the placed checkpoint from the
failed run is still on disk, and the multicycle is a constraint, not a netlist change:

```tcl
open_checkpoint E:/bob_full_v1/bob_vivado/bob.runs/impl_1/bob_top_placed.dcp
set_multicycle_path -setup 512 -from [get_clocks sysclk] -to [get_clocks sysclk]
set_multicycle_path -hold  511 -from [get_clocks sysclk] -to [get_clocks sysclk]
report_timing_summary -delay_type max -max_paths 1
```

A positive WNS there means the rebuild will close. (The later exception overrides the
256/255 pair already in the checkpoint.)

**If the rebuild still fails:** if WNS is still negative, the next gap is 10 (1024 cycles,
8192 ns) — same two places. If timing is met but the router is still congested, drop to the
8 × 8 core (64 CLBs) as planned below.

## Build (Windows)

1. Replace `E:\bob_full_v1\hw` with this `hw/` and run `build.tcl`.
2. Program the board and copy the whole `bob_vivado\out\M16\` folder to `docs/reports/M16/`.
3. On the Mac run `make check` (it requires timing closure and the single-cycle registers in `sysclk_1cycle.txt`).
4. If Vivado stops or the PC restarts, send `bob_vivado\bob.runs\synth_1\runme.log` (or `impl_1\runme.log`) and say which happened.

## Automatic (`make hwtest M=M16`)

The full M15 list on the new bitstream — the regression (idcode `0xFBEEF093`, bypass, selftest, the M7 fabric checks through the chain with **chain-length 18560**, the five frame checks, the guest designs as frames, ram-readback, blinky-rate), `bob-wide` / `pnr-wide`, the four partial-reconfiguration checks and the three BRAM-frame checks — plus:

## By hand (`--manual`)

- [ ] After `make hwtest M=M16`: SW1..0 = 00 lights LD0, 01 lights LD1, 10 lights LD2, 11 lights all three (the pipeline, as at M7)
- [ ] `./bob build work/examples/big/big.v --clock run --div 17 -o build/bit/big_run.bit`, then `./bob load build/bit/big_run.bit` (at the M16 gap this steps 1.9 times a second, half of M15's rate): with BTN0 held the LEDs flicker (the LFSR parity changes every step); releasing BTN0 freezes them; BTN1 resets to the seed (LD2 off, LD1 off, LD0 shows the seed parity)
- [ ] Partial reconfiguration still works on the big grid: `./bob build work/examples/gates/gates.v -o build/bit/gates.bit`, `./bob load build/bit/gates.bit`, then `./bob build work/examples/gates/gates.v --pcf work/examples/gates/gates_swapped.pcf -o build/bit/gates_swapped.bit` and `./bob load --partial build/bit/gates_swapped.bit`. It prints how many of the 145 frames it rewrote; with all buttons released, SW0 up and SW1 down, the LEDs go from LD1 + LD2 lit to only LD1 lit.
