bob, frame by frame

Volume 2 ended with a long word of configuration bits poured into the chip. This volume slows that moment down. It follows one real configuration, the counter example, from the Mac to the last flip-flop: through the four JTAG wires, past the TAP (the chip's doorman), into the packet parser (bob's configuration brain), cut into frames, and into the exact tiles where each frame belongs.

Each picture builds up in steps: press Next (or → on the keyboard). The words, frames, addresses and CRC are the ones bob's tools really send; the grid and the frame map come from device.json; the last chapter is Vivado's own placement of bob on the XC7Z020.

1The cable

A configuration is just bits. First they have to get from the Mac to the chip, one at a time.

The design has already been built: ./bob build turned the Verilog into one long word, the configuration, where every bit sets one switch in bob. Now ./bob load sends it.

The Mac talks USB to a Raspberry Pi Pico running DirtyJTAG. The Pico turns USB messages into JTAG: four wires, the same ones every FPGA and most chips have for testing and configuration.

JTAG (IEEE 1149.1) is slow and simple on purpose: one bit per clock, and a chip needs only four pins for it. AMD's own configuration flow (UG470) can use it too, which is why bob copies it.

2The doorman: the TAP

Before any configuration bit gets in, the chip has to agree what the bits are for. That is the TAP controller's job.

The TAP controller (Test Access Port) is a small state machine with 16 states, identical in every JTAG chip. It moves on every TCK edge, and TMS alone decides where it goes. TDI only matters in the two Shift states.

There are two branches. The IR branch loads the 6-bit instruction register: which door the next data will go through. The DR branch then pushes the data through that door.

In bob this is hw/src/core/jtag_tap6.v, instance u_tap: the only part of bob wired to the outside world's configuration pins.

3The instruction picks a door

Six bits in the instruction register decide where TDI's bits go and where TDO's come from.

Each instruction connects a different data register between TDI and TDO. Some are one bit long, some are 32, and one, CFG_IN, is as long as you like: it is a pipe into the configuration brain.

The codes are AMD's where AMD has them (CFG_IN 000101, CFG_OUT 000100, JPROGRAM, JSTART, IDCODE), so the stream looks like a real 7-series configuration.

A few are bob's own: CHAIN_IN / CHAIN_OUT load the whole memory as one long shift (the second configuration path), and CAPTURE reads every user flip-flop.

4A stream of 32-bit words

Through CFG_IN the bits arrive as 32-bit words, and the chip first has to find where a word starts.

The host sends words: 32 bits each, most significant bit first. But a stream of bits has no marks between words. So the stream starts with a sync word, AA995566, the same one every AMD bitstream uses.

The parser hunts: after every bit it checks whether the last 32 bits spell AA995566. The moment they do, it knows where every later word begins.

After the sync come packets: a header word saying which register to write and how many words follow, then the words. Most of the stream is one packet: the frames.

5Reading a packet header

One word, four fields. This is how the brain knows what the next words mean.

A type-1 header (UG470 table 5-20) packs four things into 32 bits: the header type, an opcode (write, read or nothing), a register address, and a word count.

A type-2 header carries only a big count, 27 bits. It follows a type-1 header whose count was 0: that is how the frame data, far more than 2047 words, gets announced.

In bob the parser decodes exactly these fields, in cfg_frames.v's states ST_HDR → ST_T2 → ST_DATA.

6The brain: bob's packet parser

This is the configuration station: a small machine that reads packets and writes registers.

The packet parser (hw/src/core/cfg_frames.v, instance u_frames) is bob's configuration brain. It has a sync hunter, a word register, a three-state header decoder, a handful of registers and a CRC engine.

Each register does one job: IDCODE checks the stream is meant for this chip, FAR says which frame is next, FDRI takes frame data, CMD takes commands, CRC checks nothing was garbled, STAT reports.

Press Play to feed it the counter's real stream and watch each packet land.

AMD's configuration logic has the same registers at the same addresses; bob implements the subset it needs (docs/bitstream-format.md section 10).

7One frame

The configuration memory is cut into frames: the smallest piece that can be written or read.

A frame is 4 words = 128 bits. FDRI words fill a 128-bit frame buffer; the fourth word completes it, and the frame is written into the memory at the address in FAR.

FAR, the frame address register, is split like AMD's: a block type (configuration or BRAM contents), a column, and a minor number: which frame within the column. After every frame FAR counts up by itself, so one FDRI packet can fill the whole chip.

AMD 7-series frames are 101 words, and a column there is a column of the real die. bob's are 4 words, and a column is a column of bob's grid.

8Where frames land on the grid

Frames are column-major: FAR sweeps bob's grid one column at a time, bottom to top.

FAR column 0 is the control column: the user clock's settings. FAR column c = x + 1 is grid column x: every tile of that column, bottom to top, each tile starting on a frame boundary.

A column is as many frames as its tiles need. A CLB takes 5 frames, so a column of 10 CLBs plus its routing is 51. The BRAM column needs 7, the DSP column 10, the pad columns 3 and 1.

The last step lights the frames the counter actually uses: most of a design's frames are zeros, because most of the chip is idle.

9Inside one CLB's five frames

The real bits of the counter, in the CLB that holds it.

A CLB tile's five frames each have a job. The first holds 16 crossbar selects (which pin feeds each element input) and the 48 element flags. The next two hold the four truth tables, 64 bits each. The fourth holds the last 8 selects. The fifth holds the tile's routing muxes.

Each square is one bit; a filled one is a 1. This is exactly what the frame looked like on the wire.

10Two kinds of memory cell

A frame's bits end up in two very different places, and a third copy is kept for reading back.

Flip-flop bits (routing selects, element flags) are ordinary host flip-flops in cfg_store.v. They take the whole frame on one falling TCK edge.

LUT bits (truth tables and crossbar) live inside the host's CFGLUT5 primitives, as ZUMA does. A CFGLUT5 can only be written by shifting: the loader (lut_loader.v) shifts 32 bits in over 32 TCK cycles, and only the CLB that owns the frame listens.

Every frame is also copied into a shadow block RAM. Reading back reads that copy, which saved a 128-bit wide, 256-way multiplexer: about 11,800 host LUTs.

11Checking, then starting

Nothing starts until the brain is sure every bit arrived intact.

While the frames arrive, the CRC engine folds every written word into a 32-bit CRC-32C. The host sends the value it expects; the brain compares. Equal sets CRC_OK, and only then is START accepted.

Startup is then four steps on four TCK edges: release GSR (the flip-flops leave reset), release GTS (the outputs turn on), raise GWE (flip-flops and RAMs may change), raise DONE. The design runs.

The rules are UG470's: nothing is released before the CRC has matched, and the outputs turn on before any flip-flop or RAM may change. The exact order is bob's own. AMD's default (UG470 table 5-11) releases DONE first, in phase 4, then GTS in phase 5 and GWE in phase 6, and lists no separate GSR step: until GWE rises, no flip-flop can change anyway.

In bob the startup sequencer is cfg_ctrl.v (u_ctrl), driven by the JSTART instruction.

12Reading it back

The same brain runs backwards: frames out of the chip, over TDO, to be checked.

After every load the host reads the memory back and compares it with what it sent. It arms reading (RCFG), sets FAR to 0, and asks for a READ of FDRO: every frame, in order.

The words come out through the CFG_OUT door, one bit per TCK on TDO. ./bob load reports FDRO readback verified only when all of them match.

13The brain's floor plan

Every part of bob's configuration logic, and who talks to whom.

bob is one Verilog module, bob_fpga.v, instance u_core. Around the fabric sit the parts that configure it: the TAP, the packet parser, the startup controller, the frame store with its shadow, the LUT loader, and the helpers for capture, BRAM and DSP access, the user clock and the pad ring.

The fabric itself never sees JTAG. It only sees its configuration bits, and the four global signals the brain controls: GSR, GTS, GWE and the user clock.

14Where it sits on the XC7Z020

bob is itself a design inside a real chip. Here is where Vivado put each part.

The PYNQ-Z2's chip has an ARM processor side and a programmable-logic side: a grid of slices (each 4 LUTs and 8 flip-flops), with columns of block RAM and DSP. Every dot on the right is one site, coloured by the part of bob that uses it.

The guest fabric (CLBs and routing muxes) fills most of the chip. The brain is small, and Vivado places it where its wires are short: near the JTAG pins and the frame store.
