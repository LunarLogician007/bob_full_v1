# Chapter 02: Architecture as data

*one description, and a fabric generated from the router's own graph*

Running time 3.8 min. Generated by the render of `scenes/ch02_*.py`; edit the scene, not this file.

Most FPGA projects describe their hardware twice: once for the chip and once for the tools. bob describes it once, in data, and generates everything else.

Everything about bob's architecture is one Python file, device.py. It says how big the grid is, which tile types exist and which configuration fields each one has, where the memory and multiplier columns go, and which pad is which switch or LED.

From it come the device file every tool reads, the Verilog parameters, the fabric itself, the architecture file for the VPR router, the names of every configuration feature, and through them the Python models and the board checks. Two copies of a number is a bug waiting to happen; here there is one.

Here is the grid that description produces: 14 columns by 12 rows of tiles. The outer ring is 44 I/O pads, and the corners are empty.

Inside, the columns are logic blocks, except column 3, which holds block RAM, and column 8, which holds DSP slices. A memory or a multiplier is taller than a logic block, so each one spans 5 rows, and each column holds two. That leaves exactly ten by ten logic blocks.

The board's switches and buttons sit on fixed pads on the west edge, and the LEDs on the east edge. Every other pad has no wire to the outside world: it is reached only through boundary scan, over JTAG.

device.py also writes an architecture file for VPR, the academic place-and-route tool. It describes each tile's pins: a logic block has sixteen inputs from the routing, eight outputs back to it, a carry in and out, and clock enable, reset and clock.

And it describes the wires: channels 36 tracks wide, made of unidirectional wires that each span 4 tiles, joined by Wilton switch boxes, with ten percent of the tracks reachable from each pin. These numbers follow OpenFPGA's reference architecture, and chapter four draws them.

Here is the central idea, borrowed from OpenFPGA. Instead of inventing a routing network and hoping the router can use it, bob asks VPR to build its routing resource graph from the architecture file, once, and commits that graph.

Then fabric_gen walks the graph. Every node that has more than one possible driver becomes a multiplexer in Verilog, and its select bits become configuration bits. The result is compiled by Vivado into the host.

So the router's model of the chip and the chip are the same object. A route VPR finds can always be loaded, and every mux in the hardware exists in the router's graph. If the architecture changes, the committed graph is stale on purpose, and every tool refuses to run until it is rebuilt.

Counted, the graph has 9,928 nodes. Horizontal and vertical wire segments, block output and input pins, and inside each logic block the element inputs and carry nodes of its crossbar.

8,095 of those nodes have a choice of drivers, so the fabric has 8,095 multiplexers and 28,782 select bits. The 138 direct connections, the carry chains and the DSP cascade, have no choice and so no bits.

These are the files behind this chapter. device.py and the architecture writer are written by hand; the device file, the routing graph and the fabric are generated; and the device tests check that every mux encoding and every pin agree.
